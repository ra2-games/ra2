## Recover rejected commands

A confirmed `rejected`, `next: reobserve`, or exhausted placement candidates is a recovery condition, not by itself an unresolved failure. After any failed helper, inspect its result before invoking another write, including commands grouped in a shell or tool call. Do not issue dependent production or assume a later camera order in an interrupted batch ran.

1. Use the helper's returned observation if current, otherwise observe again; check `ui.status` only if readiness or the session is in doubt. Require the same session and a ready battlefield; use a short monitor window to check frame advancement if needed. After initial start, `Battle not ready` calls for bounded readiness polling, not another start.
2. Reconcile accepted batch orders (and rejected indices when continuing independent orders), current camera, visible owned units, sidebar and production. Placement helpers pan the camera even when placement fails; return with `look` before using a last-seen unit ID. Rejection does not guarantee that native UI side effects were undone. A completed building still in production has not been placed and can occupy its construction queue; do not start another building in that queue yet.
3. Change the relevant condition before retrying: reacquire a visible target, choose a nearby reachable waypoint, wait for a transient queue condition, or select a few better foundation sites within build reach. Move visible blockers only when unit orders work. If unit clicks keep being rejected after placement attempts, consider a lingering placement interaction as a hypothesis, not a proven cause. Prefer completing the pending placement. If a revised small candidate set also fails and the pending product prevents useful control, use native `act` with `action: "cancel"` and that observed product's `type` as a recovery tradeoff, then verify the product/pending state clears. Cancellation discards the product; it is not a cursor-only reset, and it must respect any user restriction on cancellation or spending. Do not invent an Escape/right-click API or inject input.
4. Verify recovery with one applicable order and its observable effect, such as unit displacement or production progress; check `sidebarTab` for a production category switch. Resume normal strategy only after confirmation. If the same failure persists through two materially different, evidence-based recovery attempts, stop and report the failed command, observations and recovery attempts. Repeating an unchanged order or merely observing again is not a different recovery attempt.

For a timeout, `next: inspect`, unconfirmed product consumption or another uncertain outcome, pause new writes and resolve the original command first. Use its retained command ID with `commandStatus`; obtain the full session ID using `observe --raw` only for this diagnostic query, and verify it is still the same session. A submitted receipt still needs observed effects. `unknown` does not prove non-execution. If bounded receipt polling and observation cannot resolve the outcome, stop without replaying the write.
